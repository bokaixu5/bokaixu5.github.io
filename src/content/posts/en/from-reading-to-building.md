Reading papers does not automatically produce products. The leverage comes from a stable pipeline: input -> judgment -> output.

## Input layer

Each week I focus on three input types:

- core papers (to understand method boundaries)
- engineering retrospectives (to learn implementation risks)
- user feedback (to validate practical value)

## Judgment layer

I filter with three questions:

1. Is this clearly better than the current baseline?
2. Is integration cost manageable?
3. Can we validate it in two weeks?

If the answer is not yes across the board, I log it but do not implement it.

## Output layer

Every reading session must end in one of these outputs:

- a new experiment task
- an optimization ticket
- a documentation note

This turns reading into an engineering decision loop instead of passive information storage.
